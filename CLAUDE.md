# CLAUDE.md

## Project

AI form-check app, named **fitee** (formerly "Form Check"; storage keys keep the `formcheck.v1.` prefix so existing data stays). Long term: a phone app that analyzes lifting videos and adjusts the user's training program based on detected form issues. This repo is the first prototype.

**Current goal:** turn the prototype into a working app for general use: a muscle group selector, an exercise library, technique feedback for every exercise, workout programs built from the selected muscle groups, and a training log (calendar, sets, reps, weights, progress) with a coach that adapts the plan (in the spirit of MyFitnessPal, for lifting). Built in phases (see Roadmap). The original v0 goal (squat depth from a side-view video) is folded into Phase 2.

## Hard rules

- Video never leaves the device. No uploads, no analytics. Video is kept only when the user taps "Save video" after a technique check, and only on the device (IndexedDB; in the iPhone app, a file in the app's folder); otherwise the in-memory recording is discarded when the results close. (Changed at the user's request: originally no video storage at all.)
- Must run in mobile Safari and Chrome over HTTPS (needed for camera access), and as the iPhone app (iOS 17+).
- No third-party network requests. `src/privacy.ts` (imported first in `main.tsx`) blocks any cross-origin fetch/XHR/beacon, `index.html` sets a CSP with `connect-src 'self'`, and the service worker (`src/offline/sw.ts`) answers every request to another origin with a network error. Keep all three: MediaPipe tasks-vision has a built-in usage logger that POSTs to `odml.pa.googleapis.com` and can't be turned off. The service worker itself only ever requests this site's own files (to install a version and to save pose files) and never follows a redirect (one could lead to another site); the browser's own update check fetches `sw.js`. The one exception on this site is the landing page's interest list (`about/`, see Decisions): once a sign-up service is connected in `src/landing/signup.ts`, its form posts the visitor's email to that one service when they submit it (a plain form post, never fetch). Nothing else on the page reaches another site (apart from what that service's own answer may load, where it shows in the sandboxed frame under the form: the page's privacy note says so), and the app itself still makes no such request.
- The landing page (`about/`) shares the app's origin, so anything on it could read the app's data (localStorage, IndexedDB). It runs only this repo's own code: no third-party scripts, styles, fonts, images, iframes (except, once a service is connected, the sandboxed frame its answer shows in, where no script runs), embeds or analytics; it sets no cookies (the service's own answer may set its own: the page's privacy note says so) and reads none of the app's data. Its build fails if the page's script takes in code from outside `src/` (`notOwnCode` in `scripts/landing-build.ts`); `tests/landing.test.ts` fails if the built script names any storage API (localStorage, sessionStorage, IndexedDB, Cache Storage, cookies, the service worker, `navigator.storage`), and `npm run landing:check` fails if the page's own code touches one at runtime, with and without the app's worker. Its CSP is written at build time from the sign-up config. No link to the app from it ("waitlist only": the app's terms and privacy policy are drafts awaiting a lawyer's review).
- No backend and no accounts (the user chose "no login for now"). That is how the code is today, not a promise: a server with sign-ups is planned later, so the app and the landing page never say "no account" (user's request; `tests/copy.test.ts` checks the app's text, `index.html`, the manifest and the landing page, closed and connected, as a reader gets the words: across line breaks, tags and no-break spaces), and the Terms and Privacy policy describe what happens today without it. Only settings, programs, the profile, numbers (landmarks, results) and user-saved set videos are stored, and only on the device (localStorage; IndexedDB for calibration recordings, saved-set replays and videos; the iPhone app's own files, below). Exports are files saved on the device, never uploads (in the iPhone app, with iOS's Save to Files panel: the person picks the place, as with a download; never the share sheet). The offline copy (Cache Storage, `fitee-*` caches) holds only the app's own files and the pose model, never user data: nothing cross-origin, nothing but GET, no error responses, no blob:/data:/video.
- The Terms of service and Privacy policy (`src/screens/Legal.tsx`) must describe what the code actually does. Change them (and bump `TERMS_VERSION` in `src/profile.ts` so people re-accept) whenever data handling changes. They are drafts for a prototype: have a lawyer review them before a public launch. The iPhone app has its own Terms and Privacy policy (`src/native/screens/Legal.tsx`, with its open-source licences) and version (`NATIVE_TERMS_VERSION` in `src/profile.ts`, the date `NATIVE_UPDATED` gives in words): the same rule applies to them, for what the app's code does.
- **The iPhone app** (`ios/`: Capacitor 8.6.3 around the same web code, built with `npm run build:native` into `dist-native/`) keeps every rule above. It makes no network requests at all: the pose runtime and both models ship inside it, and three layers block requests: `src/privacy.ts` (imported first in `src/native/entry.ts`), the native build's CSP (`NATIVE_CSP` in `scripts/native-build.ts`: `connect-src 'self' blob: data:`, no `'unsafe-eval'`, no workers or frames), and a `WKContentRuleList` that blocks every load but `capacitor://localhost`, `blob:` and `data:` (`ios/App/App/FiteeContentRules.swift`, in place of the service worker, which a WKWebView doesn't run). The bridge gate (`FiteeViewController.swift`) stands in all three ways from the page to native code, each of them Capacitor's: its "bridge" message handler (`FiteeBridgeGate`: only fitee's own plugin (`FiteeNative`), console logging (`Console`, printed by Debug builds only) and the status bar style (`SystemBars`) can be reached, and every other native call is dropped unanswered, Capacitor's HTTP, cookie and web-view plugins under any of their names included; never add a plugin that can make a request, set cookies or change the server path to `GATE_ALLOWED` in `src/native/bridge.ts`), its UI delegate (`FiteeUIDelegate`: every `prompt()` answered with nothing, since Capacitor's reads one as a cookie request whatever the config, and no window opened, where Capacitor's would hand the URL to Safari; alert, confirm and the camera's permission go on to Capacitor's) and navigations (`FiteeNativePlugin.shouldOverrideLoad` cancels every one that isn't to `capacitor://localhost`, which Capacitor would hand to Safari). `AppInfo.gate` says all three are in place, and the self-test proves each. AirPlay is off. Saved sets (index, replays, videos) are files in `Library/Application Support/fitee/sets/` that fitee asks iOS to leave out of iCloud and computer backups (the folder and every file, at every save: guidance to iOS, so the texts say "asks iOS to leave out", never "never in a backup"); the plans, log, profile and settings stay in the web view's localStorage, with a copy in `…/fitee/data/` that is in the phone's backups, like any app's data. The temporary copies iOS gives the app of a video picked for a check or filmed with Take Video are deleted when that check ends (its results close, its analysis ends without results, or it's left while the video is analysed), once no video is being saved, no picked video is in use and the picker hasn't opened since (else with the next check's), when the picker closes without a file, at every launch (`tmp/` is emptied before the web view exists) and by Delete all my data, which also removes the web view's own stores and the cookies Capacitor copies into Foundation's store; a Delete all stopped part way (its marker, `Library/Application Support/fitee-deleting`) is finished at the next launch, before anything reads the data. Release builds never log (`loggingBehavior: 'debug'`); a Debug build's console is for CI and developers, never a tester. Never change `server.hostname` or `server.iosScheme`, and never set `server.url` (`capacitor.config.ts`): `capacitor://localhost` is where the user's data lives.
- **The web build stays byte for byte the same when the app's code changes.** Native differences sit behind `__NATIVE__` (true only in `vite build --mode native`) in the forms `scripts/native-build.ts`'s header lists, or in `src/native/`, reached only through `import()` inside such a branch or the native build's swaps (`NATIVE_SWAPS`). The web build fails if it loads `src/native/` or `@capacitor/` (`webHasNoNativeCode`); `__NATIVE__` never appears in modules the landing page, the service worker or `tools/landing-screens/seed.ts` load, and only the shared files `tests/native-flag.test.ts` lists may use it. After any change to a shared file, `tools/native-check/web-identity.sh <base> <work dir>` must say "web build identical" against the pull request's base (quote its last line in the pull request).
- Keep the live skeleton overlay working.
- UI copy calls this "technique feedback". No injury-prevention or medical claims.
- Don't add checks the landmarks can't support (e.g. no spine rounding: there are no spine landmarks). When confidence is low or the camera view can't show a check, report "couldn't judge"; never guess.
- Don't download or scrape videos from YouTube, Instagram, TikTok or any other site.

## Stack

- Vite + TypeScript + Preact, no backend
- Vitest for tests (landmark JSON fixtures, no video). `tests/tsconfig.json` adds Node types for tests only.
- MediaPipe Pose Landmarker (tasks-vision, web), running on-device
- Deploy to GitHub Pages
- iPhone app: Capacitor 8.6.3 (`@capacitor/core` and `@capacitor/ios`, exact devDependencies; no `@capacitor/cli`: `scripts/native-sync.ts` does what `cap copy ios` does), compiled from `node_modules/@capacitor/ios` by CocoaPods (the generated `Pods/` are committed; CI never runs `pod install`), iOS 17.0+, iPhone only (it also runs on iPads in compatibility mode). The app's own native code is Swift in `ios/App/App/`. No Mac in this project: GitHub's macOS runner builds and runs it in the simulator (`.github/workflows/ios.yml`).

## Roadmap

1. **Phase 1 (done):** muscle group selector, exercise library (data file), rule-based program builder, programs saved on device.
2. **Phase 2 (done):** generic form analysis engine driven by exercise config: rep segmentation, all check types, per-rep pass/fail/couldn't judge, generalized setup check, limb-proportion personalization, live recording (hands-free) and video-file analysis, results screen.
3. **Phase 3 (done):** sourced technique standards → thresholds (cited in `src/data/sources.ts` and next to each check, all still "unvalidated"). Full analysis for back squat, bench press, deadlift, overhead press, barbell row, Romanian deadlift, and later the push-up (Army and school fitness-test standards) and the reverse lunge (NSCA's forward lunge); others "basic analysis" (placement, rep counting, range of motion). The walking lunge, hip thrust and pull-up were studied for full analysis and stay basic for now: a walking lifter doesn't stay in a fixed frame, the plates hide the near hip, and a side view can't judge the chin over the bar.
4. **Phase 4 (done):** hidden calibration screen: label own reps, compare verdicts, tune thresholds, export thresholds JSON and landmark fixtures. Shipped together with: front/back camera flip, page transitions and motion, and the training log + coach (most of Phase 5).
5. **Phase 5 (done):** technique checks saved as numbers to the log; repeated faults lower load and add the corrective; consistent form progresses load (form gate on full-analysis lifts lifted with weight); technique trend per exercise; log editing (past days, edit finished workouts, notes); easier-week and behind-plan coach rules. Still open (needs real data from the user): tune the coach rules on real logs, and calibrate thresholds with real labelled reps (`src/data/calibrated.json` is empty until then).
6. **Phase 6 (in progress): iPhone app.** First the Capacitor shell around the same web code (`ios/`, the native build, the app's own texts, CI in the simulator and a dormant TestFlight job); a StoreKit subscription with its paywall, Save to Photos and the hosted privacy and support pages come in later pull requests, then TestFlight and the App Store (the launch checklist).

After each phase: open a PR, wait for the user's "merge it", then confirm the Pages deploy.

## Original v0 features (now covered by Phase 2)

1. **Setup check:** show the squat placement criteria (side-on, phone around hip height, 1x lens), then run a live check on the camera preview. Whole body in frame (nose to ankles detected with good confidence) and side-on (left and right shoulders and hips nearly overlap horizontally). Show nudges like "step back" or "turn side-on". Enable recording only when the check passes.
2. **Record** a set, or pick an existing video.
3. **Detect reps** from the hip's vertical movement. At the bottom of each rep, compare hip and knee landmark heights: depth is hit when the hip is at or below the knee, with a margin the user can tune.
4. **Results:** hit or miss per rep, the bottom frame with a skeleton overlay, and "couldn't judge" when landmarks are low-confidence.

**Out of scope:** accounts, payments.

## Decisions

- Library covers free weights, bodyweight, cables and machines. Free weights are preferred by the program builder because machines can hide joints from the camera.
- Every exercise needs: at least one fault with a cue and a corrective that is another library exercise; every check links to a listed fault; checks only use declared landmarks; symmetry checks only on front-view placements; "basic" exercises only carry range-of-motion or hold-alignment checks. `tests/library.test.ts` enforces this.
- Rep tracking uses a joint's vertical movement only, so mainly-horizontal movements (cable flys, face pulls, seated cable rows) are not in the library yet.
- "Top"/"bottom" of a rep = where the tracked joint is highest/lowest on screen. Distances in checks are fractions of torso length.
- Equipment settings: full gym (everything); dumbbells only = dumbbells + bodyweight + pull-up bar (no bench); bodyweight = bodyweight + pull-up bar. A pull-up bar is always assumed.
- Program builder: weekly sets 10/14/18 by level, each muscle 2× a week (3× with 5+ days), session caps, multi-joint first, secondary muscles count half. Unloaded bodyweight moves get higher rep ranges. `minLevel`/`maxLevel` keep advanced moves from beginners and regressions (knee push-ups) from experienced lifters. Deterministic: same inputs give the same program. It adds notes when volume is scaled down or a muscle can't be trained.
- Thresholds (Phase 3): every check has a `source` (enforced by tests). Full-analysis lifts use written standards: NSCA lifting proficiencies, IPF Technical Rules 2026, Larsen et al. 2021 (squat torso angle), Duffey & Challis 2005 (bench bar path, lowering time), ACSM 2009 (tempo), Schellenberg et al. 2013 (deadlift hip range), Soucie et al. 2011 (normal joint ranges); for the push-up the US Army's push-up test (FM 7-22, 2012, Appendix A, superseded in 2020 by ATP 7-22.01; FM 21-20, 1992, superseded in 2010 by TC 3-22.20: depth, full extension and the body line "viewed from the side"), ATP 7-22.01 (12 March 2026, para 2-59: hand-release push-up errors; it superseded the 2020 edition, whose para 2-78 has the same words) and the Connecticut Physical Fitness Assessment manual (pp. 22–23, a school fitness test); for the reverse lunge NSCA's forward lunge, Farrokhi et al. 2008, Winter 2009's segment lengths (the book wasn't opened for it: the values the code already quoted) and, for its lowering, the Army's rear lunge drill (ATP 7-22.02, 2020 incl. Change 1: slow cadence, 50 counts a minute) (where each of these was read is noted in `src/data/sources.ts`; Winter's book by its ISBN). A superseded edition is cited by its date with what superseded it, never as current. Where a standard is qualitative only, the comment and source say the number is derived. Lockout = 165° (180° minus a 15° tolerance for 2D landmark error, Wade et al. 2023). Tempo limits are in measured seconds: the engine times a phase from 5% to 95% of the tracked joint's travel, which is about two thirds of a smooth movement (`TEMPO_MEASURED_SHARE` 0.65, measured at 15–60 fps on a body moved rigidly: a 1.0 s lowering reads 0.64–0.73 s minimum-jerk, 0.73–0.80 s cosine-eased; the demos 50–75% of theirs; pinned in `tests/engine/checks.test.ts`), so ACSM's 1 s lower bound → `MIN_ECCENTRIC_SEC` 0.65 s, which passes a smooth 1.0 s lowering at about the limit for a tracked joint moving with a minimum-jerk profile (a 0.8 s one fails; the old 0.8 s limit asked for about 1.2 s). On a lift the tracked joint's own path counts too: on the demos' paths the limit falls at about 0.75–0.9 s of real lowering for the bench press and the row and about 1.0–1.15 s for the back squat, whose hip barely moves while the knees first bend (0.1–0.2 s more each with minimum-jerk progress, the squat up to 1.3 s), so each lift's own value comes from calibration with real reps; "How we judge it" says "at least 0.65 s, not counting the slow start and finish (roughly 1 s in all)", and each rep's result "target at least 0.65 s, not counting the slow start and finish" (`TEMPO_UNTIMED` in `src/data/describe.ts`). Back squat, Romanian deadlift, bench press, barbell row and reverse lunge use it; the push-up has no tempo check (the Army's push-up drill lowers in one count at its moderate cadence, 80 a minute, so in 0.75 s: FM 7-22, 2012, pp. 7-11 and 8-14, the same in ATP 7-22.02, which superseded those chapters in 2020, so a minimum of roughly 1 s would fault the push-up's own standard; and ACSM's "1–2 s ECC" goes with heavy loads, while for sets of 15–25 reps or more it recommends moderate to fast velocities, and the builder gives push-ups up to 20–25 a set), while the reverse lunge keeps its own (NSCA's "slowly flex", and the Army's rear lunge at its slow cadence, 1.2 s a count). Basic-analysis range checks carry a "draft, no published standard yet" source with normal joint ranges for context. Every threshold stays `status: 'unvalidated'` until Phase 4 calibration.
- Standards changes in Phase 3: squat depth = thighs parallel (NSCA; IPF is stricter, users can raise the margin), torso lean ≤ 60°, squat hip-path check removed (no standard); bench depth = elbows to shoulder level (IPF 2026 rule) instead of an elbow angle; deadlift set-up = hips below shoulders (NSCA) instead of a torso angle; row torso ≥ 60° from vertical (NSCA "slightly above parallel"). Added later: push-up depth = upper arms parallel (Army: "at least parallel to the ground"), read as the shoulder's centre level with the elbow's or lower with a derived 10%-of-torso tolerance as for the bench press (with the hands under the shoulders the upper arm only reaches parallel as the chest nears the floor, so where it does depends on hand placement; on the demo a rep stopping with the chest about 12 cm up still fails), elbow lockout 165°, body straight at the bottom and the top (the hip angle between shoulder and ankle ≥ 165°, derived: it sees the hips sag or pike off the shoulder–ankle line, not the back); reverse lunge depth = hip at most 1.2 torso lengths above the near toe (derived from NSCA's back knee 3–5 cm off the floor and Winter's segment lengths, 1.0–1.05 torso lengths, plus room for landmark error and proportions; both toes are on the floor at the bottom, so with the camera exactly side-on the near toe marks the floor whichever leg leads), torso ≤ 25° from vertical at the bottom (NSCA "perpendicular" plus the 15° landmark tolerance), knee lockout 165°, controlled lowering.
- The exercise page shows "Full analysis"/"Basic analysis" and a "How we judge it" list with each check's target and source; full analysis "follows written coaching, competition and fitness-test standards and published research".
- Engine: no exercise-specific code. Joint names resolve to the near side (side view, chosen by visibility) or both sides/midpoint (front view). Torso length (shoulder to hip) is the scale for distances. Reps = home → far → home turning points of the tracked joint (hysteresis = max(minAmplitude/2, 25% of movement range); reps smaller than `minAmplitude` are ignored; recordings that start or end mid-rep don't count that rep). `firstPhase` says whether the first move is eccentric or concentric (for tempo). A check judged at the top of a lift whose first move is down looks past the rep's last frame (its top) into the frames after it, within the recording: 0.3 s either side for a lockout, two frames for the others, so a lockout reached a moment after the turning point (a lunge's stepping foot landing after the hips top out) counts; past the rep's end only while the tracked joint stays within 0.07 torso lengths of where it was at the top (`STILL_AT_TOP`, its position smoothed as the signal the reps are found on), so what follows the last rep (racking the bar as the elbows straighten) doesn't pass for its lockout; an up-first lift's start stays inside the rep. The last rep's top is still the highest point after its bottom, wherever in the recording's tail that falls (as before this window), so a lifter who turns to the phone right after a soft last rep can still have it read in the turned frames.
- "Couldn't judge" whenever a check's joints are below visibility 0.6 at the key frames, under 60% coverage for whole-rep checks, or the camera angle is wrong for the rep (side-on ratio of shoulder/hip separation to torso length < 0.35, front > 0.3; setup check is stricter: < 0.25 / > 0.4). Tempo only needs the tracked joint, so it's still judged.
- Personalization: `ProportionMeter` measures thigh/shin/upper arm/forearm ÷ torso while standing side-on during setup (saved on device, numbers only); it measures on every side view, but the setup list asks the lifter to stand tall for it only where a check uses it (`usesProportions`: the back squat; a push-up's setup is in the push-up position). Rules are named in config (`personalize: 'squatTorsoLean'`), based on Winter (2009) reference proportions and a bar-over-mid-foot model, capped at ±12°.
- Recording: the live camera computes landmarks as it goes and records the video to memory (see Saved sets). Hands-free mode (default on) starts 3 s after the setup check holds and stops when the lifter stays still at the start position for 3 s after a rep, leaves the frame for 2 s, or after 3 minutes. Picked video files are read locally via an object URL at 20 fps, then released.
- Results pictures: small JPEGs of each rep's turnaround frame kept in memory only and cleared when the results screen closes. Live recordings capture them at the online turning points; files seek back to the exact frames after analysis.
- User-tuned depth margin (results screen, under "Adjust depth strictness") is stored as a threshold override in localStorage. The slider spans the check's own margin ± 0.2 torso lengths (the reverse lunge's −1.2 too, so a first touch only nudges it; widened to take in a margin saved outside that), saves hundredths, and says what the margin asks by the check's point and reference ("hip may stay up to 120% of torso above the toe").
- Exercises tab filters: muscle row plus a Filters sheet (equipment groups match if the exercise uses any selected item; "Bodyweight" = needs no weights, pull-up/dip bars and benches allowed; difficulty = the exercise's `minLevel`; compound/isolation; full analysis only). Remembered per device in localStorage.
- Design language: **heat** (the user's two brand sheets, replacing the earlier four-colour fitee look). Two themes: **Paper** (light: page `#F4ECE2`, cards Paper `#FFF9F4`, warm Ink `#1E1412` text) and **Molten** (dark: page `#151619`, cards `#222428`, Black oxide `#1B1D20`, Chrome `#D9DDE1` text, bronze `#B08D57` collars). Settings → Appearance: Automatic (follows the phone, default), Light or Dark. The logo is four plates side by side (amber, orange, flame, red) between two collars on a bar; the hero wordmark colours each letter from amber to oxblood (light) or crimson (dark). Plates per theme: light amber `#F2A21A`, orange `#EC7518`, flame `#DD4A1B`, plate red `#B5241D`, oxblood `#7A1A16`; dark amber `#F7B23B`, orange `#F48A32`, flame `#EF6235`, plate red `#E5443A`, crimson `#C9303D`. Meaning: flame is the one accent (selection, done sets, trained days, the coach, links in a darker tone); the hot gradient fills the main action buttons, ticked sets, done days and picked muscle tiles; muscle icons highlight the group in flame (no per-group colours any more). Status keeps its own colours so faults don't blur into the brand: green = clean / passed, amber = warning or couldn't judge, deep red = fault or delete. Text on fills passes WCAG AA: white on the light theme's deep flame `#C43B17` and button gradient, Black oxide on the dark theme's flame and gradient; picked tiles use 19px ExtraBold labels (large text). Placeholder text (`--placeholder`, through one app-wide `::placeholder` rule, so no field falls back to the browser's lighter grey) passes 4.5:1 on every field fill in both themes; a ticked set's empty box shows what's logged in the text colour ("BW": body weight only, "–": nothing), never the plan (an unticked set's empty boxes show the plan as grey hints; in the editor, typing a value ticks the set without filling the others). Type: Bricolage Grotesque self-hosted from `@fontsource-variable/bricolage-grotesque` (bundled by Vite, no font CDN; OFL licence in `THIRD_PARTY_NOTICES.md`), ExtraBold for headings and big numbers, regular for text, 600 for buttons and labels. Shapes: buttons and tiles are plate-rounded (16–22px), chips and search are pills. "Log a workout" in My workouts is a molten panel (dark with a flame glow) in both themes so self-logging stands out. The camera view and replays stay black in both themes; the skeleton is drawn in amber, low-confidence joints in red, result rings green (passed) / red (fault). How-to demos draw a skin-toned figure whose muscles glow on the heat ramp; equipment stays in neutral tokens.
- UI: keep it simple. Three tabs (Train, Log, Exercises); one primary action per screen; plan creation is two steps with large tappable tiles; details (weekly volume, all checks, depth tuning) go behind `<details>`. Icons are inline SVG (no icon fonts or external assets). The pose-model picker only appears on the camera test page (default: full model).
- How-to demos are animated figures, not videos (user's choice): drawn from the same camera angle as the exercise's placement, correct form by construction, no copyright or network requests, respects reduced motion (start and turnaround side by side). Demos must pass their own exercise's checks (tests/demo.test.ts); when thresholds change in Phase 3/4, fix the demo or the threshold, whichever is wrong.
- Demo figure (user's request: "human-like with muscle groups", showing "how and how much the muscle groups are being engaged" in the design language): a human body drawn from the skeleton with the ten muscle groups visible at rest in the muscle grey; working muscles glow on the heat ramp (grey, amber, orange, flame, red) by their level at that moment of the rep. The ramp has a glow stop half way to amber (`--heat-glow`): on dark a copper ember, so faint work glows warm rather than olive while amber and orange stay distinct. Chosen from a judged contest of two prototypes (athletic silhouette over an anatomy chart whose fibre lines broke the heat into stripes). Every demo has a male and a female figure (user's request: "the same animations for the female model"), picked by the profile's body drawing. The front view (standing, bent over, lying) was later redrawn for realism (user: "the front profile is really bad", "the side profile is good", so the side views stayed byte-identical), again from a judged contest of two prototypes (built up from anatomical landmarks, over one traced from the app's body icons), then reviewed and fixed. One-sided exercises (one-arm row, single-leg moves, side-lying abduction, concentration curl, kickback, cable lateral raise) light only the working side's limbs (the other side rests; `Demo.otherSide` gives it a share where it helps, e.g. the back leg of a lunge). Rules (`src/demo/engagement.ts`): main movers follow the exercise's demand curve through the three profile points (start, middle, turnaround; 1 = the hardest position; five points when the effort shifts within the rep, as in the push press), at 80% while lowering (eccentric activation is lower for the same load; exercises built around the lowering, the Nordic curl and negative pull-up, set `lowering: 1`; an assisted way back, the negative pull-up's step up off the box, sets `returnShare` so the pulling muscles rest); assisting muscles the same at their lower peak; stabilisers stay near-steady (70% of their peak plus 30% following the demand); with the load resting at the start (deadlift) everything stays near rest until it leaves the floor; holds swell gently. Peak ranges: main 0.85–1, assist 0.45–0.7, steadies 0.25–0.5. The legend lists the muscles (main first), what each does, and a live bar; it says it's a guide to typical muscle use, not a measurement. No injury or medical claims.
- Demo contact: bodies rest on surfaces (BODY thickness), never sink into the floor, benches, boxes or walls; planted feet don't slide (`npm run demo:contact`, which checks the side views). Lying front views (side plank, side-lying abduction) rest the body by `FRONT_SKIN` (the outer edge of the foot, the outer hip, the elbow (the fist by `BODY.hand`, as in the side view), the pillow arm's forearm, wrist and palm, the head on the pillow arm, the top palm on the iliac crest, and the top leg on the bottom one by the inner knee and ankle): the drawn outline touches the floor within its own width at every point of the rep, for both bodies, and stacked legs touch at the knee and the ankle (`tests/body.test.ts`). Legs that rest on each other press flat where they meet instead of passing through each other (`pressing` in `body.ts`). Barbell plates are drawn behind the lifter so they never cover the body; held props sit in the hand (`Side.hand`). The spine bends only where the real movement rounds or arches it on purpose (crunches); lifts like the deadlift, squat and row keep it neutral.
- Front-view one-sided exercises (e.g. side-lying hip abduction, cable lateral raise) read angles from the working side (the side whose tracked joint travels further) instead of averaging both sides.
- The bent-over rear delt fly is filmed and drawn from in front and above (`PLACEMENTS.frontAbove`: phone sideways at about head height or higher, 1.5–1.75 m from the feet, tilted down, `tiltDown`; the demo looks down 28° on a back nearly level, `torsoScale` -0.42, captioned "Front view from above"), so the back and the rear delts face the camera and the shoulder angle can be judged; from a level phone at hip height the bent-over trunk is seen end-on, and a phone at chest height still sees it nearly end-on. Sideways because the arms out to the sides (about 1.5 m across) only fit an upright frame from about 2–2.5 m away, where the bent-over body is too small for the setup check's "Close enough" (sideways it fits from 1.5 m; beyond about 1.75 m, or measured from the head, that advisory starts to warn). The summary and the placement note ask for a back nearly level, as the demo shows, because the 40° range check reads reliably there: modelled through checkSetup and analyze for lifters 1.55–1.95 m, the hands stay in view, the start pose sets up, and a full fly with the back nearly level reads about 43–66° (half reps are flagged), while a back hinged only 75–80° can read 36–45° on a full fly (the hip–shoulder–elbow angle is weakest where the trunk's image is about as long as the hip's inward offset).
- Push-up and reverse lunge placements (from camera models of lifters 1.55–1.95 m tall): the push-up has its own placement, the phone sideways and level on the floor 2–2.5 m from the lifter's side, centred on the body (from 2 m a tall lifter's shoulders stay in the frame at the top; past 2.5 m a short lifter fills less of it than the setup check's "Close enough" asks; off centre the setup check can take the lifter for turned, and a tilted phone shifts the depth reading), and the setup check passes in the push-up position (standing, the shoulders are above a frame shot from the floor). The reverse lunge: hip height, portrait, 3–3.5 m (from 3 m both feet stay in the frame as the back foot steps back; "Close enough" advises closer at 4 m, and at 3.5 m with the front camera), exactly side-on with the feet and hips across the frame (a body turned toward the phone passes the setup check but shifts the depth reading by about 0.07 torso lengths per 10°), a little off centre toward the way the lifter faces; either leg can lead, and the toes are required landmarks (depth is read against the near toe).
- Calibration (Phase 4): labels are per rep (fault ids; empty = good). A check is expected to fail exactly when its fault is labelled; accuracy = agreement on judged reps ("couldn't judge" is not counted), and where two checks share a fault, one that passed while the other caught the labelled fault isn't scored (`caughtByAnother`: the fault can be at one end of the rep only), in the scores, the suggestions and the per-rep marks. Suggestions sweep the threshold and only appear when they beat the current agreement. Personalization is off while calibrating so thresholds suit average proportions. Recordings (landmark numbers only) live in IndexedDB, can be exported as fixtures, and are wiped by "Delete all my data". Workflow: export thresholds JSON → merge into `src/data/calibrated.json` → commit; "Use these thresholds on this phone" saves them as local overrides instead.
- Camera: the front camera is the default (users need to see the screen to set up), mirrored in the preview; a flip button sits on the preview during setup and countdown, and the choice is remembered. The back camera gives sharper landmarks when someone else films.
- Motion: page changes use the View Transitions API (slide forward/back by route depth, fade between tabs; fallback CSS entrance where unsupported), tab pill glides, cards and rows rise in with a stagger, press feedback on tappables, toasts, counting numbers, the chart line draws in. Everything collapses to instant under `prefers-reduced-motion`. Animate only transform/opacity where possible.
- Training log: weights stored in kg and shown in kg or lb (Settings). A workout from a plan day is pre-filled with the coach's weights and reps; typing a value carries it to later unfilled sets; ticking a set fills planned values and starts a rest timer. Unticked sets are dropped when finishing. Estimated one-rep max = Epley (1985). Backup is a JSON file saved on the device (all `formcheck.v1.*` keys except `formcheck.v1.device.*`, which are about the phone rather than the user; `app: 'fitee'`); restore reads it back and also accepts older `form-check` backups.
- Coach ("AI analysis"): rule-based and on-device, not an AI service (hard rules: no network, no backend). Double progression: same weight until every set hits the top of the rep range, then add the smallest sensible step (kg: 2 dumbbell / 5 lower-body compound / 2.5 other; lb: 5 / 10 / 5), capped at 10% (ACSM 2009: 2–10%). Two sessions below the range → about 10% lighter. A fault in 2 of the last 3 technique checks → about 10% lighter, the fault's cue, and its corrective added to the workout and offered for the plan. Insights: new bests (grouped, last 7 days), stalls (no e1RM gain in 3 sessions), week progress, muscles not trained in 10 days. Next plan day = the one after the last day trained from that plan.
- Two ways to train, chosen with the switch at the top of the Train tab (remembered; default Personal trainer): **Personal trainer** (the app builds the plan and the coach adjusts weights) and **My workouts** (you log your own: empty workout, routines you save, repeat a recent workout). Both share the log, calendar, progress and technique checks. Workouts you build yourself are named after the one or two muscle groups with the most sets ("Back & Chest"). Routines store exercises and set counts only; starting one pre-fills last time's numbers for each exercise. Any finished workout can be repeated or saved as a routine.
- Bodyweight exercises (equipment only bodyweight / pull-up bar / dip bars / bench, `isBodyweight` in `src/data/filters.ts`) log body weight plus optional added weight: the weight column becomes "+kg" (empty = body weight only) and sets are stored with `bw: true` and `weight` = added kg. The app has no `prompt()`, `window.open`, `target="_blank"` or links to other sites (keep it so: they'd do nothing). **Data:** WebKit's storage in an app is best-effort (iOS can clear it when the phone is nearly full), so localStorage stays the working store and the copy in `data/` (in the phone's backups) puts it back before the app starts; a copy that can't be read stops the app at a start-error screen rather than starting empty. Saved sets move out of IndexedDB into files left out of backups (WebKit puts an origin's web storage in backups once it's a day old, so IndexedDB can't be kept out), replays with their videos, so an eviction can't orphan a video; videos cross the bridge in 1 MiB base64 chunks and play from their file's URL (Capacitor answers Range requests). Calibration recordings stay in IndexedDB (the calibration screen isn't in the app). A picked or Take Video file's temporary copy is deleted when its check ends (WebKit's file panel would keep it until the web view goes, which a killed app never reaches): the native clear empties all of `tmp/`, so it waits for every video still being saved, and doesn't run while a picked video is in use or once the picker has opened again (WebKit copies the next pick into `tmp/` before the page hears of it); that check's own end clears then. Delete all removes the app's folder, `tmp/` and the web view's stores (`WKWebsiteDataStore`: deleted rows could stay in SQLite's free pages), then reloads to Welcome; a marker written first and removed last lets the next launch finish one that stopped part way (else the user's keys, still in localStorage with no copy, would be copied back). ## Implementation notes

- The MediaPipe WASM runtime and pose model are served from this site (`public/mediapipe/`, populated by `npm run fetch-assets`), not from a CDN, so the app makes no third-party requests at runtime. The service worker keeps a copy once used (see Install and offline). In CI the models come from Google's "latest" URLs at build time; when one changes, its hash changes and phones that had saved it download it once more. The iPhone app's build pins them instead (`scripts/native-pose-files.json`, checked by `npm run build:native`, so the iOS workflow too): a new model fails it until the pins are updated, in a commit of their own, once the new model is the one wanted.
- `site/` holds an unrelated landing page and is not part of the app build (leave it alone). fitee's own landing page is `about/` (see Decisions).

## Commands

- `npm install` — installs deps and fetches MediaPipe assets (postinstall)
- `npm run dev` — dev server on all interfaces (HTTPS needed for camera on a phone; see README)
- `npm test` — run the test suite
- `npm run fixtures` — regenerate synthetic landmark fixtures
- `npm run demo:sheets -- --ids a,b --frames 5 --per 6 --out DIR` — render demos to PNG sheets (dev tool; needs Playwright; `--body female` for her figure)
- `npm run demo:contact` — contact report for demos (`DEMO_IDS=a,b` to narrow)
- `npm run typecheck` — typecheck app, tests and the service worker (`-p src/offline`)
- `npm run build` — typecheck + production build to `dist/`, including `sw.js` and the landing page in `dist/about/` (`npm run build -- --outDir DIR --emptyOutDir` builds elsewhere; `node scripts/landing-build.ts DIR` rebuilds just the page into a build folder)
- `npm run offline:check -- --work DIR --port 4180` — end-to-end install/offline/update check in Chromium (dev tool; needs Playwright)
- `npm run landing:check -- --work DIR --port 4402` — end-to-end check of the landing page in Chromium, closed and with a stand-in sign-up service on port + 1 (dev tool; needs Playwright)
- `npm run landing:screens -- --work DIR --port 4405` — re-shoot the app screens the landing page shows, with made-up sample data (dev tool; needs Playwright)
- `npm run build:native` — typecheck + the iPhone app's web build into `dist-native/` (`vite build --mode native`: no service worker or landing page; the pose files checked against their pins)
- `npm run native:sync` — copy `dist-native/` into the Xcode project, write Capacitor's two config files and the bundle ID (run before every `xcodebuild`; no Capacitor CLI)
- `npm run native:check -- --work DIR --port 4460` — Chromium check of `dist-native/` with a stand-in native side (dev tool; needs Playwright; `--keep-build yes` reuses `dist-native/`)
- `npm run app-icon` — render the iPhone app's icon into `ios/App/App/Assets.xcassets/AppIcon.appiconset/AppIcon-1024.png` (needs Playwright)
- `tools/native-check/web-identity.sh <base-ref> <work dir>` — build the web app at `<base-ref>` and from this tree and compare every file's SHA-256 ("web build identical: N files")
