# CLAUDE.md

## Project

AI form-check app, named **fitee** (formerly "Form Check"; storage keys keep the `formcheck.v1.` prefix so existing data stays). Long term: a phone app that analyzes lifting videos and adjusts the user's training program based on detected form issues. This repo is the first prototype.

**Current goal:** turn the prototype into a working app for general use: a muscle group selector, an exercise library, technique feedback for every exercise, workout programs built from the selected muscle groups, and a training log (calendar, sets, reps, weights, progress) with a coach that adapts the plan (in the spirit of MyFitnessPal, for lifting). Built in phases (see Roadmap). The original v0 goal (squat depth from a side-view video) is folded into Phase 2.

## Hard rules

- Video never leaves the device. No uploads, no analytics. Video is kept only when the user taps "Save video" after a technique check, and only on the device (IndexedDB); otherwise the in-memory recording is discarded when the results close. (Changed at the user's request: originally no video storage at all.)
- Must run in mobile Safari and Chrome over HTTPS (needed for camera access).
- No third-party network requests. `src/privacy.ts` (imported first in `main.tsx`) blocks any cross-origin fetch/XHR/beacon, `index.html` sets a CSP with `connect-src 'self'`, and the service worker (`src/offline/sw.ts`) answers every request to another origin with a network error. Keep all three: MediaPipe tasks-vision has a built-in usage logger that POSTs to `odml.pa.googleapis.com` and can't be turned off. The service worker itself only ever requests this site's own files (to install a version and to save pose files) and never follows a redirect (one could lead to another site); the browser's own update check fetches `sw.js`.
- No backend and no accounts (the user chose "no login for now"). Only settings, programs, the profile, numbers (landmarks, results) and user-saved set videos are stored, and only on the device (localStorage; IndexedDB for calibration recordings, saved-set replays and videos). Exports are files saved on the device, never uploads. The offline copy (Cache Storage, `fitee-*` caches) holds only the app's own files and the pose model, never user data: nothing cross-origin, nothing but GET, no error responses, no blob:/data:/video.
- The Terms of service and Privacy policy (`src/screens/Legal.tsx`) must describe what the code actually does. Change them (and bump `TERMS_VERSION` in `src/profile.ts` so people re-accept) whenever data handling changes. They are drafts for a prototype: have a lawyer review them before a public launch.
- Keep the live skeleton overlay working.
- UI copy calls this "technique feedback". No injury-prevention or medical claims.
- Don't add checks the landmarks can't support (e.g. no spine rounding: there are no spine landmarks). When confidence is low or the camera view can't show a check, report "couldn't judge"; never guess.
- Don't download or scrape videos from YouTube, Instagram, TikTok or any other site.

## Stack

- Vite + TypeScript + Preact, no backend
- Vitest for tests (landmark JSON fixtures, no video). `tests/tsconfig.json` adds Node types for tests only.
- MediaPipe Pose Landmarker (tasks-vision, web), running on-device
- Deploy to GitHub Pages

## Roadmap

1. **Phase 1 (done):** muscle group selector, exercise library (data file), rule-based program builder, programs saved on device.
2. **Phase 2 (done):** generic form analysis engine driven by exercise config: rep segmentation, all check types, per-rep pass/fail/couldn't judge, generalized setup check, limb-proportion personalization, live recording (hands-free) and video-file analysis, results screen.
3. **Phase 3 (done):** sourced technique standards → thresholds (cited in `src/data/sources.ts` and next to each check, all still "unvalidated"). Full analysis for back squat, bench press, deadlift, overhead press, barbell row, Romanian deadlift; others "basic analysis" (placement, rep counting, range of motion).
4. **Phase 4 (done):** hidden calibration screen: label own reps, compare verdicts, tune thresholds, export thresholds JSON and landmark fixtures. Shipped together with: front/back camera flip, page transitions and motion, and the training log + coach (most of Phase 5).
5. **Phase 5 (done):** technique checks saved as numbers to the log; repeated faults lower load and add the corrective; consistent form progresses load (form gate on full-analysis lifts); technique trend per exercise; log editing (past days, edit finished workouts, notes); easier-week and behind-plan coach rules. Still open (needs real data from the user): tune the coach rules on real logs, and calibrate thresholds with real labelled reps (`src/data/calibrated.json` is empty until then).

After each phase: open a PR, wait for the user's "merge it", then confirm the Pages deploy.

## Original v0 features (now covered by Phase 2)

1. **Setup check:** show the squat placement criteria (side-on, phone around hip height, 1x lens), then run a live check on the camera preview. Whole body in frame (nose to ankles detected with good confidence) and side-on (left and right shoulders and hips nearly overlap horizontally). Show nudges like "step back" or "turn side-on". Enable recording only when the check passes.
2. **Record** a set, or pick an existing video.
3. **Detect reps** from the hip's vertical movement. At the bottom of each rep, compare hip and knee landmark heights: depth is hit when the hip is at or below the knee, with a margin the user can tune.
4. **Results:** hit or miss per rep, the bottom frame with a skeleton overlay, and "couldn't judge" when landmarks are low-confidence.

**Out of scope:** accounts, payments.

## Decisions

- Library covers free weights, bodyweight, cables and machines. Free weights are preferred by the program builder because machines can hide joints from the camera.
- Every exercise needs: at least one fault with a cue and a corrective that is another library exercise; every check links to a listed fault; checks only use declared landmarks; symmetry checks only on front-view placements; "basic" exercises only carry range-of-motion or hold-alignment checks. `tests/library.test.ts` enforces this.
- Rep tracking uses a joint's vertical movement only, so mainly-horizontal movements (cable flys, face pulls, seated cable rows) are not in the library yet.
- "Top"/"bottom" of a rep = where the tracked joint is highest/lowest on screen. Distances in checks are fractions of torso length.
- Equipment settings: full gym (everything); dumbbells only = dumbbells + bodyweight + pull-up bar (no bench); bodyweight = bodyweight + pull-up bar. A pull-up bar is always assumed.
- Program builder: weekly sets 10/14/18 by level, each muscle 2× a week (3× with 5+ days), session caps, multi-joint first, secondary muscles count half. Unloaded bodyweight moves get higher rep ranges. `minLevel`/`maxLevel` keep advanced moves from beginners and regressions (knee push-ups) from experienced lifters. Deterministic: same inputs give the same program. It adds notes when volume is scaled down or a muscle can't be trained.
- Thresholds (Phase 3): every check has a `source` (enforced by tests). Full-analysis lifts use written standards: NSCA lifting proficiencies, IPF Technical Rules 2026, Larsen et al. 2021 (squat torso angle), Duffey & Challis 2005 (bench bar path, lowering time), ACSM 2009 (tempo), Schellenberg et al. 2013 (deadlift hip range), Soucie et al. 2011 (normal joint ranges). Where a standard is qualitative only, the comment and source say the number is derived. Lockout = 165° (180° minus a 15° tolerance for 2D landmark error, Wade et al. 2023). Tempo limits are in measured seconds (engine trims the slow ends, so ACSM's 1 s → 0.8 s). Basic-analysis range checks carry a "draft, no published standard yet" source with normal joint ranges for context. Every threshold stays `status: 'unvalidated'` until Phase 4 calibration.
- Standards changes in Phase 3: squat depth = thighs parallel (NSCA; IPF is stricter, users can raise the margin), torso lean ≤ 60°, squat hip-path check removed (no standard); bench depth = elbows to shoulder level (IPF 2026 rule) instead of an elbow angle; deadlift set-up = hips below shoulders (NSCA) instead of a torso angle; row torso ≥ 60° from vertical (NSCA "slightly above parallel").
- The exercise page shows "Full analysis"/"Basic analysis" and a "How we judge it" list with each check's target and source.
- Engine: no exercise-specific code. Joint names resolve to the near side (side view, chosen by visibility) or both sides/midpoint (front view). Torso length (shoulder to hip) is the scale for distances. Reps = home → far → home turning points of the tracked joint (hysteresis = max(minAmplitude/2, 25% of movement range); reps smaller than `minAmplitude` are ignored; recordings that start or end mid-rep don't count that rep). `firstPhase` says whether the first move is eccentric or concentric (for tempo).
- "Couldn't judge" whenever a check's joints are below visibility 0.6 at the key frames, under 60% coverage for whole-rep checks, or the camera angle is wrong for the rep (side-on ratio of shoulder/hip separation to torso length < 0.35, front > 0.3; setup check is stricter: < 0.25 / > 0.4). Tempo only needs the tracked joint, so it's still judged.
- Personalization: `ProportionMeter` measures thigh/shin/upper arm/forearm ÷ torso while standing side-on during setup (saved on device, numbers only). Rules are named in config (`personalize: 'squatTorsoLean'`), based on Winter (2009) reference proportions and a bar-over-mid-foot model, capped at ±12°.
- Recording: the live camera computes landmarks as it goes and records the video to memory (see Saved sets). Hands-free mode (default on) starts 3 s after the setup check holds and stops when the lifter stays still at the start position for 3 s after a rep, leaves the frame for 2 s, or after 3 minutes. Picked video files are read locally via an object URL at 20 fps, then released.
- Results pictures: small JPEGs of each rep's turnaround frame kept in memory only and cleared when the results screen closes. Live recordings capture them at the online turning points; files seek back to the exact frames after analysis.
- User-tuned depth margin (results screen, under "Adjust depth strictness") is stored as a threshold override in localStorage.
- Exercises tab filters: muscle row plus a Filters sheet (equipment groups match if the exercise uses any selected item; "Bodyweight" = needs no weights, pull-up/dip bars and benches allowed; difficulty = the exercise's `minLevel`; compound/isolation; full analysis only). Remembered per device in localStorage.

- Calibration (Phase 4): labels are per rep (fault ids; empty = good). A check is expected to fail exactly when its fault is labelled; accuracy = agreement on judged reps ("couldn't judge" is not counted). - Training log: weights stored in kg and shown in kg or lb (Settings). A workout from a plan day is pre-filled with the coach's weights and reps; typing a value carries it to later unfilled sets; ticking a set fills planned values and starts a rest timer. Unticked sets are dropped when finishing. Estimated one-rep max = Epley (1985). Backup is a JSON file saved on the device (all `formcheck.v1.*` keys except `formcheck.v1.device.*`, which are about the phone rather than the user; `app: 'fitee'`); restore reads it back and also accepts older `form-check` backups.
- Coach ("AI analysis"): rule-based and on-device, not an AI service (hard rules: no network, no backend). Double progression: same weight until every set hits the top of the rep range, then add the smallest sensible step (kg: 2 dumbbell / 5 lower-body compound / 2.5 other; lb: 5 / 10 / 5), capped at 10% (ACSM 2009: 2–10%). Two sessions below the range → about 10% lighter. A fault in 2 of the last 3 technique checks → about 10% lighter, the fault's cue, and its corrective added to the workout and offered for the plan. Insights: new bests (grouped, last 7 days), stalls (no e1RM gain in 3 sessions), week progress, muscles not trained in 10 days. Next plan day = the one after the last day trained from that plan.

Your body weight (optional, Settings) is saved with each workout that has bodyweight sets; load = body weight + added, used for volume and estimated max only when known. Without it, bodyweight progress charts most reps (holds chart the longest hold). Coach: bodyweight moves start at body weight, progress by reps until the top of the range, then by added weight in plain steps (2.5 kg / 5 lb, no 10% cap since the body is most of the load); bodyweight-only records compare reps or hold time.

- Form gate (Phase 5, "consistent form progresses load"): on full-analysis lifts, when every set reached the top of the range the coach adds weight only if the latest technique check in the last 21 days had at least 80% clean reps (reps with no failed check; "couldn't judge" doesn't count against). No recent check → kind `check`: same weight, "check form first", and the workout card links to the technique check; a clean check during that workout shows "Use {next weight}" which moves the unfinished sets up. Latest check with faults → same weight until a clean check. Basic-analysis, bodyweight-only and your own exercises aren't gated. - Install and offline (user's request: "Install it like an app and use it offline… with the pose model cached on the phone. Nothing leaves the device"): a small hand-written service worker, no Workbox, so every line on the phone can be audited (`sw.js` is unminified). Registered only in production builds in a secure context. **What is saved when:** the app itself (every file but `mediapipe/`, about 0.9 MB) when the worker installs; the pose runtime this browser uses (SIMD, else no-SIMD) and the full model (about 24 MB) by themselves in an installed app (display-mode standalone or iOS `navigator.standalone`; an iPhone home-screen app has its own storage, so it saves them on its own first launch online) once the terms are accepted (they describe it; nothing is downloaded while the Welcome screen shows), not where the browser reports Data Saver (`navigator.connection.saveData`: Chrome on Android; iPhones don't report Low Data Mode to websites, and the privacy policy says so), not for a week after the phone couldn't keep it (the worker's markers, see No room), and not while a new version installs or waits; on "Save for offline use"; and whenever a technique check or the camera test loads them (save on use); the other runtime and the lite model on use. A one-off visit in a tab never downloads the pose files unless a check is opened. While the pose model saves, every screen but Settings shows "Saving for offline use: X of 24 MB. Keep fitee open until it's done." (closing the app stops it; the next launch online carries on), then a "Ready to use offline" toast. **Caches:** the app's is named by the hash of its files (`fitee-app-<hash>`); each pose file has its own, named by that file's hash (`fitee-pose-<file hash>`). A deploy that changes only the app keeps every pose file where it is; one that changes a pose file (e.g. CI fetching a newer model) leaves the others in place, so an update needs room only for the changed file, and pose files saved while an update waits are still saved once it applies. A new version copies unchanged app files from the old caches, downloads only changed ones (`?v=<hash>`, `cache: 'no-store'`: past the HTTP cache and the CDN; `no-store` rather than `reload`, so no second copy lands in the HTTP cache), checks each download's size and SHA-256 against the list before storing it under its clean URL, and downloads a changed pose file only if the phone had saved the old one, and installs only once the new copy is kept: an update never leaves the phone without a pose file it had saved (deleting the old copy at activation would stop technique checks working offline after Settings said "Ready to use offline"). Without room for the new copy (or for any of the app's own files, which must all be kept), the install fails, deletes the app cache it made (on a full phone its room counts; unchanged files are copied again next time, nothing downloaded), and tells every open page (`install-no-room`, with the room it needs: everything it writes, its copy of the app's files included); the current version keeps running, offline too. The browser tries an update at every launch: a file the phone couldn't keep recently isn't written again (see No room: a week for a pose file, a day for one of the app's own), so those tries fail at once with nothing downloaded, until that has passed or the user taps Try again (on a nearly full disk Chromium can lose a marker when the browser restarts, so a launch may download the update's files again sooner; the privacy policy says so). Data Saver doesn't stop an update downloading a new copy of a pose file the phone had saved (the privacy policy says so). Before any download (installing, or a file used for the first time) it looks in the browser's own HTTP cache (`only-if-cached`, never the network, stale copies included), under the file's own URL and then under its download URL (`?v=<hash>`, where a copy fetched while the phone couldn't keep it lands), and keeps that copy only if its size and SHA-256 match: the first visit doesn't download the app twice, pose files a phone used before the service worker existed aren't downloaded again, and once the phone has room a save keeps what went through the HTTP cache meanwhile. No request the worker makes follows a redirect (`redirect: 'error'`; a redirect could lead to another site, e.g. every github.io file once a site moves to a custom domain). A file already on its way is downloaded once: a second request for it (a technique check opened while "Save for offline use" runs) waits for the first. If Cache Storage itself fails, requests go to the network, so the app still opens online. **No room:** a file that downloaded and matched its size and SHA-256 but that the browser refused to store counts as one the phone couldn't keep, whatever the error: over quota it's `QuotaExceededError`, but on a really full disk Chromium throws `UnknownError` ("Unexpected internal error"), and its storage estimate shows a fixed headroom (quota = usage + 1 GiB) however full the disk is. So the estimate is only a cheap first check, acted on where it does show a shortage (the worker before downloading a pose file or a changed one an update needs, and in answer to a save, before anything is downloaded); no room by the estimate counts as couldn't keep too. The worker remembers it with an empty cache named for the file and the time, `fitee-unkept-<hash>-<ms>` (it holds nothing; the name outlives the worker, which the browser stops when idle, and a new version installing; where Cache Storage can't even hold that, in memory while the worker runs). Pose files are held back for a week (`NO_ROOM_RETRY_MS`), the app's own files for a day (`APP_NO_ROOM_RETRY_MS`: they're small, about 0.9 MB in all, and an app update shouldn't wait a week once there's room; Chromium's free space near zero comes and goes). The period runs from the first time: a recent mark stays as it is; a later failure replaces an older mark (a time ahead of the clock, a clock put back, doesn't count). For that period nothing downloads the file again by itself: a technique check gets a pose file through the HTTP cache, unsaved (`cache: 'default'` under `?v=<hash>`: a repeat comes from there where the HTTP cache can hold it; on a really full disk or with a small HTTP cache a big file may not fit, and is downloaded again), an install that needs the file fails at once (above), and the installed app's own save waits. The status reports, per pose file, when the phone couldn't keep it (`unkeptAt`; `noRoom` = any pose file): Settings says "This phone couldn't keep the pose model (24 MB), most likely for lack of space. Free up some space, then try again." (not "check your connection"), the installed app's auto-save waits the week (`poseUnkeptAt`: the latest such time among the files a technique check needs), and a technique check that can't load the model offline says the phone couldn't keep it instead of promising it will work offline. A mark goes when the file is kept; activation keeps the marks of its own pose files (the room the deleted caches took often comes back only after the browser restarts, so trying again at once would fail and start a new week) and deletes the rest. "Save for offline use", Try again and the auto-save first send the worker `{ type: 'save', urls }`: it answers `{ go: false }` (and marks them) when the estimate already shows no room for them all, else tries once more to keep each file even within its week (if refused again, the week still runs from the first time). "Try again" for a new version that needed more room, or for the app's first save, deletes all the marks from the page (that version's worker isn't running to ask), then tries at once. **A newer version on the site:** a download that comes back OK but isn't this version's file (size or hash) means the site already serves a newer version (a stale copy in the HTTP cache or a download cut off half-way doesn't count; tested); the worker reports it (`newer`), and after a save that ended that way (or during which a newer version took over from another window) the app looks for the update. With it waiting, Settings says "The new version has a new pose model: tap Update and save to get it."; before it's on the phone (GitHub Pages' CDN can serve the old `sw.js` for up to 10 minutes after a deploy), "The pose model has changed online, but the new version of fitee isn't on this phone yet. Try again in a few minutes.", and Try again then looks for the new version (`registration.update()`, waiting for it to install) and downloads nothing until it's here; if it couldn't install for lack of room, it says that. **Saving while an update waits:** whenever a new version waits, the save button reads "Update and save": it applies the update first (the running version can't keep a pose file the update changed: the site already serves the new one) and carries on saving after the reload (`formcheck.v1.device.saveAfterUpdate` in sessionStorage, removed as soon as it's read; that save runs once the worker has answered and the terms are accepted, and never applies an update itself, so it can't loop). If the update still hasn't taken over after the reload (the running version was busy, e.g. sending a file to another tab, so the switch waits), the save doesn't run on the old version: the page asks the new version again and waits up to a minute for it to take over (then it reloads into it and saves), else stands down and the button offers it again. The installed app's own save doesn't start while a new version installs or waits; it runs once the update has applied (a fresh page) or at the next launch. Activation deletes this app's caches the new version doesn't use, never other caches. A failed install stores nothing the current version uses; the browser retries at its next update check, reusing what was saved. An install ends by checking, by cache name, that every file it kept is there (a version activating meanwhile, e.g. "Update now" on the one before, deletes caches it doesn't use) and fails otherwise, so it is retried instead of activating with an empty copy. A first install that fails (the browser then drops the registration) shows "Couldn't save the app for offline use" with "Try again" in Settings (never "Saving the app…" for good), and the app registers again by itself when the phone comes back online or the app comes back to the front; not when it failed for lack of room (the worker said so): then Settings says "This phone couldn't keep it (0.9 MB), most likely for lack of space. Free up some space, then try again." (when the browser wouldn't even register it, `AbortError`, as Chromium does on a nearly full disk until it restarts: "This phone couldn't keep it, most likely for lack of space. Free up some space; it tries again the next time you open fitee."; a page a version already controls just asks it what's saved), and it's tried at the next launch (which, within the day, fails at once with nothing downloaded; on a disk so full that even the marker's name couldn't be saved, it downloads the app once more) or on Try again (which forgets the marks). **Keep `sw.js` at this URL for good:** a 404 or a redirect on it makes every update check fail, and phones keep the old version, which answers every visit from its cache. To take offline use out, or before moving the app to another address, deploy a `sw.js` that deletes the `fitee-*` caches, calls `self.registration.unregister()` and has no fetch handler, and leave it up until phones have picked it up. **Updates:** a new version waits. It applies by itself only within 15 s of the app opening (or coming back after 30 min away), on a screen where a reload loses nothing: never during a technique check, the camera test, a workout being logged or edited (or any active workout), a routine, the profile, plan creation or the dev pages, and never while typing. Otherwise Settings shows "A new version is ready" with "Update now" (which reloads into it if another window already applied it), and the browser applies it the next time the app opens from cold. The app checks for a new version when it comes back after an hour or more. **Delete all my data** keeps the offline copy (it holds no user data; the confirm, Settings and the privacy policy say so); removing it means clearing the site's data (or deleting the iPhone home-screen app), which deletes the user's data too. The Install row: "Installed on this phone"; Chrome's install prompt as an "Install fitee" button (Chrome's own install banner isn't suppressed: the button is offered as well); iPhone/iPad: Share, then Add to Home Screen, then open it once while online and leave it open until it has saved the pose model (it has its own storage, so it saves itself and the pose model on that first launch; opened first with no signal it can't load), and a note that it keeps its own data apart from Safari (or the other browser it was added from: back up there, restore in the app); otherwise a one-line hint. Offline row: checking (the worker hasn't answered yet), saving the app, couldn't save the app (Try again; for lack of room, it says so), ready (with MB), saving the pose model (progress), app saved but not the pose model ("The app works offline" and "Save for offline use" with what it downloads; after a problem the heading is "The pose model isn't saved" and the line, in the amber warning colour, says why: the phone couldn't keep it, a newer version on the site, or failed; the button reads "Update and save" whenever a new version waits, and the line then points to it, else "Try again" after a problem), not available. Sizes keep a no-break space before "MB". Update row: "A new version is ready" ("Update now"), or "A new version needs more space" ("It needs about 9.4 MB of free space on this phone. Until then this version keeps working, offline too. Free up some space, then try again.", with Try again). A technique check that can't load the model offline says "The pose model isn't saved on this phone yet. Connect to the internet and keep fitee open while it loads; after that, technique checks work offline." with "Try again" (also retried by itself when back online), or, where the phone couldn't keep it, "This phone couldn't keep the pose model (most likely for lack of space), so technique checks need a connection here. Free up some space, then save it in Settings.". On the camera test, a model that isn't saved when the other one is says to choose that one, and the model picker stays usable after a failed load (only locked while a model loads). `navigator.storage.persist()` is asked once the pose files are saved in an installed app. iOS: status bar style `default` (the page starts below the status bar; the bottom bars pad for the home indicator).

## Implementation notes

- The MediaPipe WASM runtime and pose model are served from this site (`public/mediapipe/`, populated by `npm run fetch-assets`), not from a CDN, so the app makes no third-party requests at runtime. The service worker keeps a copy once used (see Install and offline). In CI the models come from Google's "latest" URLs at build time; when one changes, its hash changes and phones that had saved it download it once more.
- `site/` holds an unrelated landing page and is not part of the app build.

## Commands

- `npm install` — installs deps and fetches MediaPipe assets (postinstall)
- `npm run dev` — dev server on all interfaces (HTTPS needed for camera on a phone; see README)
- `npm test` — run the test suite
- `npm run fixtures` — regenerate synthetic landmark fixtures
- `npm run demo:sheets -- --ids a,b --frames 5 --per 6 --out DIR` — render demos to PNG sheets (dev tool; needs Playwright; `--body female` for her figure)
- `npm run demo:contact` — contact report for demos (`DEMO_IDS=a,b` to narrow)
- `npm run typecheck` — typecheck app, tests and the service worker (`-p src/offline`)
- `npm run build` — typecheck + production build to `dist/`, including `sw.js` (`npm run build -- --outDir DIR --emptyOutDir` builds elsewhere)
- `npm run offline:check -- --work DIR --port 4180` — end-to-end install/offline/update check in Chromium (dev tool; needs Playwright)
